## Why this transaction

Found by scanning a single, already-finalized historical mainnet block (~2 weeks old at the time of the search) for `transfer(address,uint256)`-shaped calls to the USDC contract, then filtering for a transaction whose receipt contains **exactly one log total** — the ERC20 `Transfer` event itself, nothing else. This is the cleanest possible fixture: zero ambiguity in log attribution, independent of the adapter's own ambiguity-handling logic (which is separately tested against deliberately ambiguous synthetic fixtures — see `../mutation-tests.md`).

## From real transaction to `ProposalActionContext`

This transaction is an ordinary EOA-invoked ERC20 transfer, so its `input` field is selector-prefixed (`0xa9059cbb...`) — the standard ABI-encoded call, selector included. Governor Bravo, by contrast, stores `signature` and `calldata` as two separate fields with **no** selector in `calldata` (Gate 2 finding — see `evidence/governor/bravo-methodology.md`). To feed this real transaction through the same adapter a Bravo-authorized action would use, the script strips the first 4 bytes (`("0x" + tx.input.slice(10))`) and sets `signature: "transfer(address,uint256)"` separately — exactly mirroring how this same transfer would be represented had it been a Bravo-authorized action instead of a direct call. Both the original selector-prefixed `rawTxInput` and the derived `bravoStyleCalldata` are recorded in `fixture.json` for transparency.
