# Gate 12 §35/§36/§37 — resource exhaustion, rate limiting, logging audit

## §35/§36 — Cost-abuse and rate-limiting

The headline item — see finding F-04 in `findings.md` for full detail. Summary: the known limitation ("public receipt Q&A lacked rate limiting") was confirmed still present (zero rate limiting or length bound existed anywhere in `apps/web` before this gate), and fixed with the smallest mechanism proportionate to the product: a 2000-character question cap and a 5-requests-per-60-seconds per-caller-key sliding window, applied to all four agent Server Actions via one chokepoint. Explicitly NOT built: a distributed rate limiter or new paid infrastructure (Redis/Vercel KV) — the honest limitation (per-instance, best-effort) is documented in the code itself and in `findings.md`, not hidden.

**Other public/mutating endpoints considered for abuse**: Cactus resolution (`/app/new`) — bounded by the same allowlist as SSRF (`ssrf-audit.md`); each resolution is one outbound fetch to a fixed, small set of hosts, not itself a meaningfully cheap amplification vector, and not independently rate-limited this gate (lower cost-per-call than an LLM request by orders of magnitude — deprioritized). RPC reads (Governor authorization re-verification) — bounded by however many ARM attempts a session can make, which is itself now CAS-protected (F-01) but not rate-limited; a determined caller could still spam ARM attempts against a single job, each triggering a real RPC read, but this costs the operator's own RPC provider quota (not a third-party metered API charged per-request the way OpenRouter/Anthropic is), and repeated ARM attempts against an already-ARMED job simply fail the CAS check cheaply. Auth brute force — the real secret-gated path (`x-demo-token` header) has no explicit lockout/backoff; given the constant-time-comparison fix (this gate) and that a brute-force attempt against an unknown, sufficiently-random token string is already impractical at network speed, this was not separately rate-limited. Sandbox mutation spam — bounded by the same auth boundary discussed in F-03 (weak, but not free of friction — requires visiting the site and submitting a form first).

**Proposal URL length / user question length / stored event metadata / historical scripts / Cactus response size**: `MAX_AGENT_QUESTION_LENGTH` (2000 chars) now bounds the one clearly user-controlled, cost-relevant string. No other input was found to be unboundedly large in a way that matters for this product's actual attack surface (Cactus responses are bounded by the runtime's own default body-size handling; stored event metadata is generated by this app's own code, not directly user-supplied free text beyond `actor`/`reason` strings, which are small by construction of the UI forms feeding them, though NOT server-side length-capped — a minor gap, S4, not fixed this gate).

## §37 — Logging audit

Grep across `apps/web/src` and `packages/*/src` for `console.log`/`console.error`/`logger`/`debug`: the only intentional logging found is `packages/db/src/migrate.ts`'s progress lines (filenames/counts only, confirmed never the connection string) and porsager/postgres's own `onnotice` handler (explicitly suppressed, `postgres-fulfillment-job-store.ts`, "never logs query parameters" per its own comment). No log statement anywhere prints a full `process.env` object, an authorization header, a cookie value, `DATABASE_URL`, raw KeeperHub/OpenRouter response bodies, or a session token. Error objects thrown to the caller are consistently the typed, message-only error classes (`PersistenceError`, `AgentProviderError`, `UnauthenticatedError`, `CactusResolutionError`, etc.) rather than raw driver/stack output — re-confirmed by this gate's own new work (F-07's fix specifically closed the one place a raw driver error could have leaked past this pattern).
