## KEEPERHUB-WIRING-001 — the live web app's APPROVE flow computed and persisted `EXECUTING` but never actually called KeeperHub; no code path existed from a real ARMED job to AWAITING_APPROVAL at all

**SEVERITY: N/A (capability gap, not a defect)** — recorded here because this project tracks every non-trivial change as a finding-shaped record, not because anything here was broken by a prior gate. The disclosed submission limitation this closes: "KeeperHub execution is proven but not yet wired to the public web app."
**SUBSYSTEM:** new `apps/web/src/lib/execution/{prepare,approve-and-execute,keeperhub-config,errors,verified-governor-deployments}.ts`; `apps/web/src/app/app/actions.ts`; `apps/web/src/app/api/fulfillment/{approve,prepare,reconcile}/route.ts`; `apps/web/src/app/app/fulfillments/[id]/page.tsx`; `apps/web/src/app/proof/[id]/page.tsx`; `packages/core/src/fulfillment-job.ts` (additive `receipt`/`executionState` fields).
**ROOT CAUSE (why APPROVE previously stopped before KeeperHub):** two compounding gaps, both real. (1) `approveFulfillmentJob` (Gate 4, unmodified) only ever moves `AWAITING_APPROVAL → EXECUTING` — it was never anyone's job to call KeeperHub afterward, and nothing did. (2) More fundamentally, no code existed that could even get a real, freshly-armed job TO `AWAITING_APPROVAL` in the first place: the state machine's own `ARMED → WAITING_ELIGIBILITY → ELIGIBLE → VERIFYING_LIFECYCLE → VERIFYING_AUTHORIZATION → CAPTURING_PRESTATE → SIMULATING → AWAITING_APPROVAL` pipeline was fully defined in `packages/core`'s transition table since Gate 4/5, and fully proven end-to-end by `scripts/gate5-keeperhub-execute.ts` as a one-shot offline script — but the live web app never walked it. This was explicit, documented, and deliberate (`apps/web/src/lib/fulfillment-actions.test.ts`: "AWAITING_APPROVAL is only reachable through live eligibility/simulation resolution, which this sandbox deliberately does not implement... no fabricated state progression"; the fulfillment detail page's own banner: "the live eligibility-to-execution orchestration for a newly-armed real proposal is out of scope here").
**FIX:** Two new orchestration modules reuse every existing proven primitive unmodified — `resolveGovernorAuthorization`, `resolveBravoLifecycleEligibility`, `buildBravoExecutionPlan`, `evaluateCallerCompatibility`, `validateLifecycleExecutionPolicy`, `simulateContractCall`, `executeContractCall`, `hashContractCall`, `ERC20TransferAdapter`, `reconcileForMarkedReceipt`, `computeReceiptHash`, and the state machine's `transition()` at every single hop — no second execution implementation, no weakened checks, no new transition edges added to the state machine.
- `prepare.ts` (`prepareJobForApproval`): ARMED → the full eligibility/lifecycle/authorization/pre-state/simulation pipeline → AWAITING_APPROVAL, or the exact matching refusal/blocked/externally-fulfilled terminal state. Read-only against the blockchain (only ever calls `simulateContractCall`, never `executeContractCall`); one CAS-guarded write from ARMED to the terminal outcome, so a crash mid-pipeline just leaves the job safely at ARMED.
- `approve-and-execute.ts` (`approveAndExecuteJob` + `continueReconciliation`): full pre-broadcast revalidation (Gate 5 Part 9's own discipline) *before* calling the unmodified `approveFulfillmentJob`, specifically because the state machine has no edge from `EXECUTING` back to a refusal state — reordering was necessary to avoid ever needing one. Then: idempotency claim (`tryClaimExecution`, Gate 7's mechanism, previously unused by the app) → `executeContractCall`, gated behind a new, independent, default-off `MARKED_ENABLE_KEEPERHUB_EXECUTION` flag → durable checkpoints at RECONCILING/WAITING_FINALITY/VERIFYING_GOVERNOR_STATE/VERIFYING_POSTCONDITION → a real `MarkedReceipt` (now persisted on the job itself, an additive `FulfillmentJob.receipt` field) → FULFILLED_VERIFIED or FULFILLED_UNVERIFIED. `continueReconciliation` is separately callable and never dispatches, so a "Refresh status" click or a fresh serverless instance after the one that dispatched was recycled safely resumes.
- The recovery-sandbox job is routed to the old, unchanged `approveJob` (state-only, no KeeperHub) at the one call site that decides which pipeline a job enters (`apps/web/src/app/app/actions.ts`/`.../api/fulfillment/approve/route.ts`), never inside the execution module itself — preserving its documented "never calls KeeperHub" guarantee exactly.
**SECURITY INVARIANTS:** the browser supplies only a `jobId`; every execution parameter (target, calldata, value, chain, proposalId) is rebuilt server-side from the job's frozen commitment via `buildBravoExecutionPlan`, never accepted from the request. `KEEPERHUB_API_KEY` is read only in `apps/web/src/lib/execution/keeperhub-config.ts`, a server-only module never imported by a `"use client"` file. `MARKED_ENABLE_KEEPERHUB_EXECUTION` defaults off and is checked before any state mutation or network call.
**REGRESSION TEST:** `apps/web/src/lib/execution/{prepare,approve-and-execute}.test.ts` (25 new tests) — double-APPROVE (asserts at most one real `executeContractCall` dispatch, via the actual mocked-fetch call log, not an inference), unauthenticated/wrong-state/live-execution-disabled refusals with zero state mutation and zero network calls, lifecycle/authorization/simulation-revert refusals before any approval is recorded, full happy-path to FULFILLED_VERIFIED with a real persisted receipt, a balance-mismatch path reaching FULFILLED_UNVERIFIED (never FULFILLED_VERIFIED) even though KeeperHub itself reported success, and resumption from WAITING_FINALITY without a fresh dispatch.
**STATUS: FIXED, VERIFIED.**
**EVIDENCE:** `evidence/system-audit/keeperhub-execution-wiring.md`.

## KEEPERHUB-WIRING-002 — two narrow, honest gaps found while wiring: a caller-authority model that (correctly) blocks every real-world governor except the one Gate 5 source-diffed, and one unhandled state-machine edge for a post-execution Governor-state disagreement

**SEVERITY: S3 (medium)** — neither is reachable without `MARKED_ENABLE_KEEPERHUB_EXECUTION=true` (off on this deployment) and a real testnet write; both are honestly surfaced (a clear refusal reason, or a clear "needs manual reconciliation" message) rather than silently mishandled.
**SUBSYSTEM:** `apps/web/src/lib/execution/verified-governor-deployments.ts`; `apps/web/src/lib/execution/approve-and-execute.ts` (`continueReconciliation`'s `VERIFYING_GOVERNOR_STATE` step).
**FINDING 1:** `evaluateCallerCompatibility` (`packages/governor/src/caller-authority.ts`, Gate 2/5, unmodified) requires `deploymentMatchesReferenceSource` — a real, human-performed source diff confirming one specific deployed contract's `execute()`/`queue()` are byte-for-byte identical to Compound's reference Bravo source. Gate 5 performed that diff for exactly one controlled Sepolia governor. No automated mechanism exists to produce this fact for an arbitrary newly-resolved governor, so `prepareJobForApproval` honestly returns `deploymentMatchesReferenceSource: false` (→ `INCONCLUSIVE` → `BLOCKED_CALLER_NOT_AUTHORIZED`) for every real-world Cactus proposal except that one already-executed governor — meaning the wired pipeline, while fully functional and tested, cannot today reach `AWAITING_APPROVAL` for any fresh, unexecuted, real-world proposal. This is not a bug introduced by this task; it is an honest reflection of a pre-existing limitation in the caller-authority model, made newly *observable* because this task is the first thing that ever exercised it against a real job. **Not fixed** — the correct fix (an automated per-deployment bytecode/source comparison) is new capability, out of this task's explicit scope ("do not expand Governor support").
**FINDING 2:** if a transaction is included but the Governor's `state()`/`executed` flag does not confirm `Executed` afterward (e.g. a reverted receipt, or a genuine Governor/relayer disagreement), the job has nowhere to legally transition — `VERIFYING_GOVERNOR_STATE`'s only edges in the existing, unmodified state machine are `["VERIFYING_POSTCONDITION", "GOVERNOR_EXECUTION_CONFIRMED"]`, neither of which fits. `scripts/gate5-keeperhub-execute.ts` never had to handle this (its one real execution succeeded). `continueReconciliation` reports this honestly ("needs manual reconciliation") and leaves the job at `VERIFYING_GOVERNOR_STATE` rather than inventing a new transition edge. **Not fixed** — adding a new refusal edge here is a real, narrow state-machine change deliberately left to a human decision rather than made unilaterally mid-task.
**STATUS: ACKNOWLEDGED, not fixed.**
**EVIDENCE:** `evidence/system-audit/keeperhub-execution-wiring.md`.

## CACTUS-LIVE-002 — Clicking "Resolve proposal" on the live production deployment silently dropped the `url` field from the outgoing request, because the loading-state fix disabled the exact form field the browser was about to read

**SEVERITY: S2 (high)** — a real, live-reported failure of the product's single primary user action (resolving a proposal), reproducible on demand, with no error shown to the user — a genuine silent failure, not merely a diagnostic-quality issue.
**SUBSYSTEM:** `apps/web/src/components/app/ProposalIntakeForm.tsx`.
**ASSUMPTION:** "Setting `disabled` on a form field inside that same form's `onSubmit` handler only affects rendering, not what gets submitted." False — per the HTML living standard's form submission algorithm, a form's outgoing entry list is constructed from its controls' state only *after* the `submit` event's handlers finish running, and disabled controls are excluded from that entry list by every browser.
**REPRODUCTION:** A live user report against the real deployed app (`web-delta-eight-44.vercel.app/app/new`): typed a real, valid proposal URL, clicked "Resolve proposal," and the page reloaded with nothing shown — no error, in both a normal window and Incognito (ruling out a browser extension). The user captured the actual browser request: `GET /app/new?` — the query string entirely empty, no `url=` parameter at all, despite the field being filled in. Direct `curl` requests against the same live deployment with `?url=<value>` explicitly present in the URL confirmed the server-side resolution itself was correct and unaffected (ruling out a server, caching, or RPC-timeout explanation first, before looking client-side).
**OBSERVED (before fix):** `<input name="url" ... disabled={resolving} />` — the submit handler called `setResolving(true)` synchronously, React flushed `disabled=true` to the input's DOM node, and the browser's own subsequent step (building the GET query string from current form-control state) then excluded that now-disabled field entirely. The resulting navigation carried no `url` value, landing back on the plain empty-state page — indistinguishable from "nothing happened."
**EXPECTED:** The typed URL must always reach the server exactly once "Resolve proposal" is clicked, regardless of any loading-state UI applied to the same field.
**ROOT CAUSE:** Disabling the one form control whose value the browser was about to read for its own native submission, from inside that submission's own event handler — a direct race against the browser's own form-data-set construction step, which the disabling side always wins in practice (React's synchronous state flush completes before the browser's post-event default action runs).
**FIX:** Changed the `url` input from `disabled={resolving}` to `readOnly={resolving}`. A read-only control is never excluded from form submission by any browser, at any timing — this removes the race entirely rather than tuning it (no `setTimeout`/`requestAnimationFrame` deferral, no browser-specific special-casing). The submit button remains `disabled={resolving}` safely, since it carries no `name`/`value` pair and therefore never contributes to the GET query string regardless of its disabled state. Visual dimming during the resolving state now uses the `read-only:` Tailwind variant instead of `disabled:`.
**IMPACT AFTER FIX:** The `url` field is now structurally guaranteed to survive submission in every resolving-state transition; the class of bug (a data-bearing control disabled inside its own form's submit handler) cannot recur through this component.
**REGRESSION TEST:** `apps/web/src/components/app/ProposalIntakeForm.test.tsx` (new file, 3 tests) — asserts the `url` input is never `disabled` after submit and still carries its typed value; asserts the resolving state still gives visible feedback (`readOnly`, `aria-busy`, disabled button) without excluding the field; asserts empty-field client-side validation still blocks submission without ever disabling the input. Verified meaningful by temporarily reverting to `disabled={resolving}` and confirming the first two tests fail with exactly the predicted assertion mismatch, then restoring the fix and re-confirming all three pass. Required adding `@testing-library/react` and `jsdom` as new `apps/web` devDependencies (this is the first DOM-level component test in the repository; every prior test was logic-only) and setting `esbuild.jsx: "automatic"` in `apps/web/vitest.config.ts` (esbuild was falling back to the classic `React.createElement` transform because `tsconfig.json` sets `"jsx": "preserve"` for Next's own SWC compiler, causing a `ReferenceError: React is not defined` until fixed). `jsdom` was pinned to `30.0.1` rather than the just-published `30.1.0` (0 days old at the time, flagged by pnpm's minimum-release-age supply-chain gate) to avoid depending on an unaged release.
**STATUS: FIXED, VERIFIED** (reproduced failing before the fix via the regression test, passing after, full monorepo regression clean).
**EVIDENCE:** this entry; live reproduction details in the conversation record (real production request/response headers captured directly from the user's browser and via direct `curl` against the same live URL).

## CACTUS-LIVE-001 — Real Cactus proposals on chains outside a narrow hardcoded list received a generic "chain unsupported" error instead of the accurate "Governor family unsupported" diagnosis, because the same chain registry was independently duplicated in three places and one copy fell out of sync

**SEVERITY: S3 (medium)** — operationally significant (a real, live Cactus-indexed proposal produced a less-accurate, less-actionable error than it should have), but not a security issue, not a silent failure, and not incorrect execution: the affected case still failed closed with SOME typed, non-crashing error at every layer tested.
**SUBSYSTEM:** `apps/web/src/lib/governance.ts`, `packages/governor/src/{resolve,verify-existence}.ts`.
**ASSUMPTION:** "The set of chains Marked can open a live RPC client against is small and static enough that three independently hand-maintained copies of the same `Record<number, Chain>` map will never drift." False the moment a real Cactus-indexed proposal existed on a chain only some of the three copies had been updated for.
**REPRODUCTION:** A live user report of two specific real proposal URLs (ENS mainnet, Optimism L2) both appearing to silently fail during interactive testing. Reproduced outside the UI first, per instruction: called the actual production `resolveCactusProposal`/`resolveGovernanceIntake` functions directly via `tsx` against both URLs plus the two Gate 1A fixtures (Compound #220, Uniswap #20), and separately made raw HTTP requests to inspect the live Cactus `__NEXT_DATA__` payload shape for all four. Full transcript and matrix: `evidence/system-audit/cactus-live-compatibility.md`.
**OBSERVED (before fix):** Cactus resolution succeeded for all four URLs — including both real proposals, with their full 77/78-digit uint256-scale proposal ids preserved exactly, no precision loss anywhere in the pipeline (the investigation's other leading hypothesis, thoroughly disproven — see below). ENS (chain 1, already in every copy of the registry) correctly reached the Governor-family probe and was accurately diagnosed `UNSUPPORTED_GOVERNOR_FAMILY` (its real Governor is OpenZeppelin Governor, not Bravo). Optimism (chain 10) was **not** in `apps/web/src/lib/governance.ts`'s independent copy of the chain registry — `resolveGovernorAuthorization` threw `GovernorResolutionError("UNSUPPORTED_CHAIN", ...)` before the family probe ever ran, producing the less-accurate, less-actionable "This chain isn't supported yet" message instead. Direct HTTP requests to the actual rendered `/app/new` page (the same request the "Resolve proposal" button's plain GET-form submission performs) showed correct, typed, human-readable results for BOTH cases even before this fix — this investigation could not reproduce a literal blank/silent page through the server-rendering pipeline itself, the authoritative production code path (see "what remains honestly unresolved" in the compatibility-matrix evidence file).
**ROOT CAUSE:** The exact same `CHAINS_BY_ID: Record<number, Chain>` map existed independently in three files (`packages/governor/src/resolve.ts`, `packages/governor/src/verify-existence.ts`, `apps/web/src/lib/governance.ts`), hand-maintained separately with no shared source of truth. One copy (the web app's) was missing chain 10.
**PRIMARY HYPOTHESES TESTED AND RULED OUT** (per explicit instruction not to assume a root cause without reproducing it):
- *Cactus page-shape change* (ScopeLift's August 2026 report taken seriously): disproven — identical `pageProps`/`proposal` object key shapes observed live across all four URLs.
- *Proposal-id precision loss through `Number()` coercion*: disproven — a repo-wide grep found zero `Number()`/`parseInt()`/`parseFloat()` calls on any proposalId field anywhere in the codebase; every proposalId field is typed `string` end-to-end; `BigInt(...)` is used only at the two legitimate on-chain-call/ABI-encoding boundaries, both exact for decimal strings. Made permanent via `packages/cactus/src/proposal-id-losslessness.test.ts` (18 tests) and a new boundary-value suite in `packages/core/src/hash-domains.test.ts` (10 tests), covering `0, 1, 220, 2^53-1, 2^53, 2^256-1`, and the exact real ENS/Optimism ids.
**FIX:** Centralized the registry into one new module, `packages/governor/src/supported-chains.ts` (`SUPPORTED_CHAINS`/`chainById`, exported from the package), and updated all three call sites to use it instead of independent copies. Added Optimism (chain 10, via viem's built-in `optimism` chain, with an optional `OPTIMISM_RPC_URL` env var falling back to the public default RPC — same pattern as mainnet). No new blockchain-write capability was added; this only expands read-only RPC reach for the Governor-family probe. Also added `export const dynamic = "force-dynamic"` to `/app/new/page.tsx`, which was missing it while every sibling DB/RPC-backed page had it (a real inconsistency, and a correction to an inaccurate claim the Gate 12 audit itself had made) — not traced to a live bug, added for consistency and defense in depth. Also captured and surfaced Cactus's own DAO-paused signal (`organization.isPaused`/`pauseReason`, previously silently discarded) as an explicit, clearly-labeled context banner on `/app/new` — never treated as execution authority, consistent with DEC-001.
**IMPACT AFTER FIX:** Optimism now reaches the same accurate `UNSUPPORTED_GOVERNOR_FAMILY`-class diagnosis as ENS (`familySupported: false`, `fulfillability.outcome: "UNSUPPORTED_AUTHORIZATION"`), verified via both a direct `tsx` reproduction and a real HTTP request against the rendered page.
**LIVE COMPATIBILITY RESULT:** Re-tested against 9 real, distinct DAOs spanning 4 different Governor implementations (Governor Bravo, OpenZeppelin Governor, GovernorAlpha, a custom Aave governor) and 2 chains. Cactus resolution: 9/9 succeeded. Governor-family support: 2/9 (Compound, Uniswap — both real Bravo deployments). The other 7 were each correctly, specifically diagnosed — zero silent failures, zero generic errors for a reason that was actually about Governor support rather than Cactus. Notably, two DAOs Cactus itself labels `"governorbravo"` (Nouns DAO, Instadapp) were correctly found unsupported by Marked's live capability probe — real, concrete field evidence for why BUILD_CONTRACT law 42 requires a live probe rather than trusting Cactus's own metadata label.
**REGRESSION TEST:** `packages/cactus/src/ssr-fallback.test.ts` (2 new tests, real-shaped ENS/Optimism sanitized fixtures, including the pause-state field), `packages/cactus/src/proposal-id-losslessness.test.ts` (new file, 18 tests), `packages/core/src/hash-domains.test.ts` (10 new tests), `packages/cactus/src/live-compatibility.test.ts` (new file, opt-in live network test against the real URLs — `MARKED_RUN_LIVE_CACTUS_TESTS=true`, verified both to skip cleanly by default and to genuinely pass live).
**STATUS: FIXED, VERIFIED.**
**EVIDENCE:** `evidence/system-audit/cactus-live-compatibility.md`.

## F-01 — TOCTOU race in ARM/APPROVE/DISARM: two concurrent mutations from the same read snapshot could both silently "succeed," duplicating events or overwriting each other's outcome

**SEVERITY: S2 (high)**
**SUBSYSTEM:** `apps/web/src/lib/fulfillment-actions.ts`
**ASSUMPTION:** "Only one ARM/APPROVE/DISARM request will ever be in flight for a given job at a given moment" — never stated explicitly, but implicit in using an unconditional upsert (`saveJobAndEvents`) for a decision computed from a job snapshot read moments earlier.
**REPRODUCTION:** Two genuinely independent `SqliteFulfillmentJobStore` instances on the same file; `Promise.all([disarmDemoJob(storeA, ...), disarmDemoJob(storeB, ...)])` racing DISARM against the same ARMED job. See `apps/web/src/lib/fulfillment-actions.test.ts`, "Gate 12: two concurrent DISARM calls..." and "...a concurrent APPROVE and DISARM racing from AWAITING_APPROVAL...".
**OBSERVED (before fix):** Both calls returned success (no error). The event log gained TWO `DISARMED` events for one user intent. In the APPROVE/DISARM race, whichever write landed last silently won — the loser's caller was told "success" while their action had no lasting effect and nothing told them so.
**EXPECTED:** Exactly one of two racing mutations from the same snapshot may apply; the other must be refused with a clear "this changed underneath you" error.
**ROOT CAUSE:** `armJob`/`disarmJob`/`approveJob`/`armDemoJob` called `store.saveJobAndEvents(nextJob, [event])` — an unconditional `INSERT ... ON CONFLICT DO UPDATE` — instead of `store.saveWithCas(nextJob, [event], job.status)`, the compare-and-set primitive Gate 11 built and proved for exactly this purpose but which was never actually wired into the application's own mutation path.
**IMPACT:** No fund-loss or unauthorized on-chain execution is possible through this path today — see F-06 (the live web app never actually calls KeeperHub; ARM/APPROVE/DISARM only move an internal status). The real impact is audit-trail integrity (duplicate events misrepresenting what happened) and a human safety property (a DISARM intended to stop a job could be silently overwritten). This matters more once execution actually gets wired into the live app (a natural next step), so it was fixed now while cheap rather than deferred.
**FIX:** All four call sites now use `store.saveWithCas(nextJob, [event], job.status)` via a new `saveWithCasOrThrow` helper, throwing `ConcurrentJobModificationError` when the CAS loses.
**REGRESSION TEST:** `apps/web/src/lib/fulfillment-actions.test.ts` — two new tests, both using genuinely independent store instances raced via `Promise.all` (not sequential awaits), asserting exactly one caller succeeds, exactly one event/outcome is recorded, and the loser receives `ConcurrentJobModificationError`.
**STATUS: FIXED, VERIFIED** (reproduced failing before the fix, passing after, re-run clean in full regression).
**EVIDENCE:** `evidence/system-audit/concurrency-audit.md`.

## F-02 — `pnpm test` could destructively wipe whatever database `DATABASE_URL` points at, with no confirmation that it's a disposable test database

**SEVERITY: S1 (critical)**
**SUBSYSTEM:** `packages/db/src/postgres-fulfillment-job-store.contract.test.ts`, `packages/db/src/postgres-fulfillment-job-store.hosted.test.ts`
**ASSUMPTION:** "Whatever `DATABASE_URL` is set in this environment when tests run is always disposable and dedicated to this test suite." True in Gate 11's own development flow; not a safe general assumption — a CI runner or developer machine could have a real `DATABASE_URL` set for an unrelated reason (a deployment preview, an already-migrated shared dev database).
**REPRODUCTION (of the risk, not of actual data loss):** Before the fix, running `DATABASE_URL=<any reachable Postgres> pnpm test` from `packages/db` unconditionally executed `DELETE FROM job_events`, `DELETE FROM execution_claims`, `DELETE FROM fulfillment_jobs` before every contract test, and multiple `INSERT`/idempotent-DDL statements from the hosted test file — with no check of any kind on what that database was for.
**EXPECTED (Gate 12 §33's own explicit bar):** Explicit test-mode opt-in, an identifiable test database/schema, a guard before destructive cleanup.
**ROOT CAUSE:** The Gate 11 `resetBeforeEach` hook and the hosted test file's direct table writes were gated only on "is `DATABASE_URL` set and reachable," never on any second signal that the target database is meant for this.
**FIX:** New `packages/db/src/live-postgres-test-guard.ts` — `checkDestructiveDbTestGuard()` requires BOTH `DATABASE_URL` set AND `MARKED_ALLOW_DESTRUCTIVE_DB_TESTS=true` (exact string) before either live test file so much as opens a connection. Without the second flag, every test in both files reports an explicit, descriptive `it.skip`, never a silent pass and never a connection attempt.
**REGRESSION TEST:** Manually verified both directions: `DATABASE_URL` set without the flag → all 5 test files (2 Postgres + 3 SQLite/in-memory) report skip for the Postgres ones with the guard's exact reason text; `DATABASE_URL` + `MARKED_ALLOW_DESTRUCTIVE_DB_TESTS=true` → the suite runs for real against the hosted database (16/17 passed in one run, one flaked on Neon cold-start latency — a known, already-documented characteristic, not a new bug).
**STATUS: FIXED, VERIFIED.**
**EVIDENCE:** `evidence/system-audit/database-audit.md`.

## F-03 — The cookie-based "Enter demo workspace" login provides no real secret-knowledge gate; the token check is a server-side self-comparison

**SEVERITY: S1 by the letter of the severity model ("auth bypass for mutation" is a named S1 example) — see mitigating context below before treating this as equivalent to a production auth bypass.**
**SUBSYSTEM:** `apps/web/src/app/app/actions.ts` (`enterDemoWorkspace`), `apps/web/src/lib/session.ts` (`sessionAuthParams`), `packages/core/src/auth.ts` (`requireAuthenticatedActor`).
**ASSUMPTION (the code's own doc comments state this is INTENTIONAL, not a bug):** "A judge never sees or types `MARKED_DEMO_SESSION_TOKEN`... they type a display name" (`actions.ts:13-14`). The mechanism: `enterDemoWorkspace` mints a session cookie (`SESSION_COOKIE="1"`) whenever a non-empty name is submitted AND the server has some token configured — it never asks the client for that token. Later, `sessionAuthParams()` reads the session flag and, if set, supplies `providedToken = process.env["MARKED_DEMO_SESSION_TOKEN"]` — i.e. the server compares its own env value against itself. The `!==`/now constant-time comparison in `requireAuthenticatedActor` can never fail for a request that went through this cookie path.
**REPRODUCTION:** Read `apps/web/src/app/app/actions.ts:19-29` and `apps/web/src/lib/session.ts:24-28` directly — no exploit needed; this is the code's literal, documented behavior. Confirmed independently by direct file reads, not solely by the investigating subagent's report.
**OBSERVED:** Any visitor who reaches `/app` can obtain a fully "authenticated" session, with an arbitrary self-chosen `actor` name (recorded permanently on every event they cause), without ever knowing the real `MARKED_DEMO_SESSION_TOKEN`. Because there is no per-job ownership check anywhere in `armJob`/`disarmJob`/`approveJob`, that session can ARM/APPROVE/DISARM **any** job by id — including one a different visitor resolved — not just a self-created one.
**WHY THIS IS NOT BEING TREATED AS A BLOCKING S0/S1 REQUIRING A REDESIGN:**
1. It is a **documented, deliberate hackathon-demo UX decision** (Gate 7/9R), not a bug slipped in unnoticed — the code's own comments state the intent plainly.
2. The demo dashboard (`/app`, `store.listJobs()`) already shows every job to every "logged in" visitor by design — this is architected as a shared sandbox, not a private per-user workspace, so "any authenticated visitor can act on any job" is consistent with (not a violation of) the product's own apparent intent.
3. **Most importantly: it cannot reach a real, unauthorized blockchain effect.** Per F-06, the deployed web app has no code path to KeeperHub's `executeContractCall` at all — ARM/APPROVE only move an internal status. The actual authority boundary (Governor re-verification before ARM, KeeperHub/Governor's own on-chain caller checks were execution ever wired in) is independent of this session check and unaffected by it.
4. A "real" fix (requiring the visitor to actually know the secret token) would directly contradict the product's own stated design goal ("a judge never sees or types the token") — i.e. it is a scope/product change, which Gate 12's own fix policy (§53) says to document and refer to the user rather than silently change.
**NARROW, SAFE IMPROVEMENTS APPLIED (do not change the core design, reduce adjacent risk):**
- `Secure` cookie flag was previously never set on either auth cookie (real gap, unrelated to the tautology above) — now set whenever `NEXT_PUBLIC_APP_ENV !== "development"`.
- Token comparison changed from a plain `!==` to a constant-time comparison (relevant to the one path — the raw `x-demo-token` header path — where a real secret is actually being compared).
**WHAT WAS NOT CHANGED, AND WHY:** The core "type a name, get a session" flow. Changing it is a product-scope decision, not a narrow security fix — see "Exact user decision required" in `gate12-result.md`.

## F-04 — Public, unauthenticated agent/LLM Server Actions had no rate limit and no input-length bound — a real, exploitable API-cost-abuse vector

**SEVERITY: S2 (high)**
**SUBSYSTEM:** `apps/web/src/lib/agent/actions.ts` — all four exported Server Actions, most acutely `askAboutReceipt` (reachable from the fully public `/proof/[id]` page with zero login).
**ASSUMPTION:** None stated; simply absent. Confirmed via direct grep: no rate-limiting code, no `middleware.ts`, anywhere in `apps/web` before this fix.
**REPRODUCTION:** Called `askAboutFulfillment` six times in under a second from the same caller key in a test — all six previously would have reached the (mocked) provider; a sufuciently long `question` string had no cap either.
**OBSERVED (before fix):** Unlimited anonymous calls, each spending real metered OpenRouter/Anthropic quota, with no per-request or per-window limit, and no cap on `question` length (itself a cost lever — a very long prompt costs more).
**EXPECTED:** A real, previously-documented known-limitation ("public receipt Q&A lacked rate limiting") should either no longer exist, or should be confirmed and fixed, per the Gate 12 prompt's explicit instruction not to hide a cost-abuse vulnerability.
**FIX:** New `apps/web/src/lib/agent/rate-limit.ts` — a 2000-character question cap, and a 5-requests-per-60-seconds sliding window keyed by the caller's forwarded IP (falling back to a shared fixed key, never to "unlimited," when no IP is available). Wired into all four Server Actions via one `guardAgentRequest` chokepoint in `actions.ts`.
**HONEST LIMITATION (documented, not hidden):** This is a per-serverless-instance, in-memory limiter — not a distributed one. A cold start resets it; traffic spread across many warm instances each get an independent budget. It meaningfully raises the cost of casual/naive abuse; it is not a defense against a determined, distributed attacker. A production deployment expecting real adversarial traffic would need a shared store (Vercel KV/Upstash) — deliberately not introduced here per the "no new paid infrastructure" instruction.
**REGRESSION TEST:** `apps/web/src/lib/agent/rate-limit.test.ts` (6 unit tests on the limiter itself) + two new integration tests in `apps/web/src/lib/agent/actions.test.ts` proving the guard is actually wired in end-to-end (a too-long question and a 6th-in-window request are both refused before the mocked provider is ever called).
**STATUS: FIXED, VERIFIED.**
**EVIDENCE:** `evidence/system-audit/abuse-audit.md`.
