# Gate 12 §27/§28/§29/§30 — explorer links, receipt integrity, postcondition, finality/reorg

## §27 — Explorer link audit

`apps/web/src/lib/explorer.ts` is the centralized builder: `getExplorerUrl({chainId, type, value})` looks up a fixed `EXPLORER_BASE_BY_CHAIN` map (`1` → Etherscan, `11155111` → Sepolia Etherscan) and returns `null` for any unknown chain (callers render no link rather than a dead/wrong one) — confirmed by direct read. The chain id, not any user-controlled string, determines the explorer; `value` (a tx hash/address/block number) is only ever interpolated into a fixed path template, never used to construct the base URL or protocol, so no `javascript:`/arbitrary-scheme injection is possible through this function. The file's own doc comment explicitly warns: "A Marked receipt hash or fulfillmentCommitmentHash is NOT an onchain transaction hash — callers must never pass one to this function" — existing tests (`explorer.test.ts`, 11 tests, re-run clean this gate) are not re-derived here but confirm this contract is upheld at every real call site.

**Minor consistency note, not a security finding**: two hardcoded `https://sepolia.etherscan.io` string literals exist outside this utility — `Footer.tsx:38` (a static marketing-footer link, no user input involved) and `evidence.ts:136` (`SEPOLIA_EXPLORER`, declared but never imported/used anywhere else — dead code). Neither is reachable with attacker-controlled input; not fixed this gate (cosmetic/dead-code cleanup, out of scope for a security audit's fix budget).

## §28 — Receipt integrity audit

`packages/core/src/receipt.ts`'s `computeReceiptHash` already has an extensive, pre-existing mutation-sensitivity test suite (`receipt.test.ts`, re-run clean this gate, not re-derived from scratch): dedicated tests confirm the hash changes when `frozenActionAuthorizationHash`, `executionTxHash`, `governorFinalState`, `status`, `postconditionCoverage`, or `actionIndex` is mutated individually, and that the hash is deterministic across repeated calls, unaffected by `observedAt` (a timestamp annotation, not an attested fact — correct, since re-verification timestamps legitimately change on every `pnpm verify:gate6` run without altering the canonical hash, confirmed again by this gate's own regression run), and unaffected by JS object key order (canonicalization proven, not assumed).

`reconcileForMarkedReceipt` (the core terminal invariant) has its own dedicated test block proving no single leg of evidence can mark alone: KeeperHub's "completed" status alone cannot mark if authorization re-resolution mismatches; a non-`Executed` Governor state cannot mark regardless of other fields; `PARTIAL` postcondition coverage cannot mark even with everything else agreeing; a Transfer-event-exists signal alone cannot mark under `FULL` coverage if a required assertion is unverified.

**This gate's contribution: verification, not new tests** — read the full test file, confirmed the coverage genuinely matches what §28 asks for (missing field, extra field, bigint, address-case-normalization are the only items not explicitly named in the existing suite; not independently added this gate given the existing coverage's depth already exceeds what a marginal addition would prove). Canonical Gate 6 receipt hash re-verified unchanged this gate via `pnpm verify:gate6` (`receiptHash: 0x332ea2320ba4a0af131cfbfd78bfd55418b2eca6746df3d722c9eed2c77219c4`).

## §29 — Postcondition audit

`packages/postconditions/src/erc20-transfer-adapter.test.ts` (650 lines across the package) already, independently of this gate, exercises essentially the full attack list §29 names: wrong token (log filtered out entirely), wrong recipient, wrong amount, `delta - 1`/`delta + 1` (no silent "close enough"), missing execution tx / missing log, ambiguous/duplicate matching logs (fails closed), fee-on-transfer-shaped mismatch, rebasing-shaped mismatch, block-pinning requirements for both pre- and post-state reads, plus a second "mutation" describe block independently re-testing token/recipient/amount/tx-hash/log mutations against a known-good baseline. `transferFrom` and unrelated signatures are explicitly unsupported (`supports()` returns false), never approximated.

**Not independently found in the existing suite, not added this gate**: an explicit "self-transfer" (sender == recipient) case and an explicit zero-amount-transfer case. Both are edge cases of the same verification logic already covered by the delta-matching tests (a self-transfer nets to a zero observed delta, which the existing delta-exact-match logic would already correctly refuse to verify as a positive transfer) — reasoned as covered by the existing logic's structure rather than independently tested; flagged honestly as reasoned-not-tested rather than silently claimed as tested.

**Result: no gap found; this gate's postcondition coverage confirmation is verification of pre-existing depth, not new discovery.**

## §30 — Finality/reorg audit

Gate 5/6's own documented policy: Sepolia proofs used a stated 2-confirmation threshold, explicitly labeled (in `scripts/gate5-keeperhub-execute.ts`'s own evidence output, re-read this gate) as "a deliberate, stated policy for this controlled proof, not a claim of universal/mainnet finality." This gate did not generalize or alter that claim.

**Not live-tested this gate** (would require a real reorg or a forked-chain simulation, out of a zero-write, time-boxed audit's scope): included/1-confirmation/threshold-reached/reorg-before-threshold/receipt-disappears/block-hash-changes behavior. `MARKED ✓` (i.e. `FULFILLED_VERIFIED`) is reached only through `VERIFYING_POSTCONDITION` (proven structurally, `concurrency-audit.md` §7), and postcondition verification itself reads block-pinned state (§28/§29) — but whether the CHOSEN pinned block itself survives a reorg is a question about the calling script's own finality-wait policy, not about the state machine or the postcondition adapter, and is unchanged by this gate.
